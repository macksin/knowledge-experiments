# Knowledge MCP — Design

A local-first, production-leaning **MCP server for knowledge & memory**.

## The motivating question

> *Are "facts", "things I learned along the way", and "my preferences / ways of thinking" the same thing — or different?*

They are **different** — they are distinct cognitive memory systems. But the reason
they *feel* like one thing is that they all enter through the same door (lived
experience) and only **separate later, through a consolidation process**. That
process is the heart of this system.

---

## 1. The four-type taxonomy

The user's three intuitive buckets map cleanly onto four memory systems from
cognitive science (Tulving's semantic/episodic split; procedural memory; and the
self-schema from social cognition):

| Type | "Knowing…" | What it holds | User's words |
|---|---|---|---|
| `semantic` | …*that* | decontextualized facts about the **world** | "facts" |
| `episodic` | …*when/where* | time-stamped personal events with provenance | the raw "**along the way**" |
| `procedural` | …*how* | skills, heuristics, strategies ("when X, do Z") | strategies |
| `self_schema` | …*who I am* | preferences, values, dispositions, mental models — about **the user** | "**how I think about problems**" |

These are the members of the `MemoryType` enum (`src/knowledge_mcp/models.py`).

### The key insight: "learned along the way" is a *process*, not a type

Everything is **captured as `episodic`** — cheap, time-stamped, with provenance.
The nightly **dreaming** job (Phase 3) **consolidates** those episodes into
`semantic` facts, `procedural` strategies, and `self_schema` updates. This is
literally Karpathy's "system prompt learning" and the cognitive-science
sleep-consolidation story.

**The dreaming phase is the answer to the motivating question:** the three kinds
of knowledge enter as one stream; the night job separates them.

### Cross-cutting fields on every memory

`source` (provenance), bitemporal validity (`valid_from`/`valid_to` +
`created_at`/`expired_at`), `confidence`, and `consolidation_state`
(`raw` → `consolidated`).

## 2. Architecture — two paths

```
        ┌──────────────────────── FAST PATH (sync MCP tools, daytime) ────────────────────────┐
        │  remember ──▶ capture as time-stamped episode ──▶ contextualize ──▶ embed ──▶ index   │
        │  recall   ──▶ hybrid retrieval (vector + BM25 → RRF → rerank) + graph context          │
        │  link / timeline ──▶ bitemporal edges & point-in-time history                          │
        └───────────────────────────────────────────────┬──────────────────────────────────────┘
                                                         │   one interface
                                              ┌──────────▼───────────┐
                                              │   MemoryStore (seam)  │
                                              │  SQLite (MVP) ──▶ PG  │
                                              └──────────▲───────────┘
        ┌──────────────────────── SLOW PATH (the "dreaming" job, nightly) ─────────────────────┐
        │  extract ──▶ consolidate (episodic → semantic/procedural/self_schema) ──▶ detect &     │
        │  invalidate contradictions (bitemporal) ──▶ rebuild blurbs + indexes ──▶ lint          │
        └───────────────────────────────────────────────────────────────────────────────────────┘
```

- **Fast path** (synchronous, this MVP): capture & retrieve only. Cheap, no heavy
  reasoning. Everything lands as a time-stamped episode; retrieval is hybrid
  contextual search + graph neighbors.
- **Slow path** (the dreaming job, Phase 3): the expensive reasoning — extraction,
  consolidation, contradiction handling, index rebuild, lint, self-schema update.
  It needs concurrency (a worker writing while reads happen), which is one of the
  reasons **Postgres is the production target**.

## 3. Retrieval — Anthropic Contextual Retrieval, adapted to memories

Reproducible locally; with prompt caching the contextualization step runs at
~$1 per million document tokens. Anthropic reports this stack cuts retrieval
failures by ~67%.

1. **Contextual blurb** per memory, generated by Claude with prompt caching and
   **prepended before indexing**. For memories (vs. documents), the "surrounding
   document" role is played by **graph neighbors** — the parent project, the source
   thread, linked entities. (`retrieval/contextual.py`)
2. Index the contextualized text into **both** a **vector** index (`sqlite-vec` /
   pgvector) and a **BM25** index (SQLite **FTS5** / Postgres FTS). (`store/`)
3. Fuse the two rankings with **Reciprocal Rank Fusion** (k≈60), over-retrieving
   ~150 candidates from each. (`retrieval/hybrid.py`)
4. **Rerank** the top ~20 with a cross-encoder (`bge-reranker-v2-m3`, local) down
   to the final `k`. (`retrieval/rerank.py`)

### Offline-first providers

Each external dependency sits behind a small interface with a deterministic,
network-free fallback, so the whole pipeline runs and is testable with no API key
and no model download. Real backends are selected automatically when available:

| Provider | Offline fallback (default) | Real backend (when available) |
|---|---|---|
| `Embedder` | `HashEmbedder` (hashed bag-of-tokens, L2-norm, 384-dim) | `fastembed` bge-small |
| `Reranker` | `IdentityReranker` (keep RRF order) | `sentence-transformers` cross-encoder |
| `Contextualizer` | `NoOpContextualizer` (empty blurb) | Anthropic (prompt-cached) |

The hash embedder and bge-small both emit 384-dim vectors, so the `vec0` schema is
stable across the offline→real swap. Selection lives in `config.py`; tests inject
the offline providers explicitly so they never depend on auto-detection.

## 4. Graph — bitemporal (Graphiti/Zep model)

Edges carry **valid-time** (`valid_from`/`valid_to`: true *in the world*) and
**transaction-time** (`created_at`/`expired_at`: believed *by the system*). The two
are independent and composable:

- A relation that **stopped being true in the world** has its `valid_to` set; the
  row stays *believed* and remains visible to point-in-time queries inside its old
  window. (valid-time close)
- A row that was **wrong and corrected** has its `expired_at` set; it drops out of
  current reads but is retained for audit. (transaction-time retraction)

**Contradictions never delete.** The point-in-time predicate
(`graph/queries.py`, `ACTIVE_AS_OF`) is:

```sql
valid_from <= :as_of AND (valid_to IS NULL OR valid_to > :as_of) AND expired_at IS NULL
```

### Worked example — "project focus A → B"

Project Helix focuses on objective **A** from `t0`. At `t1`, the focus shifts to
**B**. This is a *valid-time* change:

1. Edge `A` is created with `valid_from = t0`.
2. At the cutover, `close_edge(A, valid_to=t1)` — valid-time only, so A stays
   believed.
3. Edge `B` is added with `valid_from = t1`.

A `recall`/`timeline` query `as_of` an instant before `t1` returns **A**; `as_of`
after `t1` returns **B**. Both rows coexist forever. (See `tests/test_bitemporal.py`.)

Nodes = entities / memories / annotations. Edges = typed relations
(`FOCUSES_ON`, `LEADS`, `CAUSES`, `BEFORE`, `MENTIONS`, `CONFLICTS_WITH`,
`ANNOTATES`, …). Annotations are first-class linked nodes (Phase 2).

## 5. MCP tool surface

**Fast path (Phase 1, implemented):**

- `remember(content, type?, source?, occurred_at?, links?)` — store a memory
  (defaults to `episodic`) with provenance + timestamp; optional links create edges.
- `recall(query, as_of?, types?, k?)` — hybrid contextual retrieval; optional
  **point-in-time** `as_of`; returns memories + scores + graph context.
- `link(from_id, to_id, relation, valid_from?, valid_to?)` — create a typed
  bitemporal edge.
- `timeline(entity_or_topic)` — full edge history / point-in-time view (the A→B case).

**Designed-for, later phases:** `annotate` and `get_entity`/`search_entities`
(Phase 2); `dream_now()` / `dream_status()` (Phase 3).

## 6. Storage — DB-canonical, SQLite → Postgres

Storage is **DB-canonical** (not markdown-in-git, which couples the source of truth
to a file format and fights concurrency). Markdown is an **I/O format only**.

A single `MemoryStore` interface (`store/base.py`) is the seam. The MVP implements
it over **SQLite** (`sqlite-vec` + FTS5); Phase 4 implements the identical
interface over **Postgres** (pgvector + FTS / ParadeDB, edge tables or Apache AGE).
The conformance suite (`tests/test_store_conformance.py`) runs unchanged against
both — that is what makes the graduation a *swap*, not a rewrite.

## 7. Comparison to prior art

No existing system combines all of: markdown-friendly I/O + **bitemporal** validity
+ Anthropic **Contextual Retrieval** + the four-type **semantic/episodic/
procedural/self-schema** taxonomy + a nightly **consolidation** job. That
intersection is the unfilled niche this project targets.

| System | File-friendly | Bitemporal | Contextual Retrieval | 4-type taxonomy | Dreaming/consolidation |
|---|---|---|---|---|---|
| basic-memory | ✅ (markdown-as-source) | ❌ | ❌ | ❌ | ❌ |
| Graphiti / Zep | ❌ (Neo4j) | ✅ | partial | ❌ | partial |
| Memento | ❌ | ❌ | ❌ | partial | ❌ |
| Honcho | ❌ | ❌ | ❌ | partial (user model) | partial |
| LangMem | ❌ | ❌ | ❌ | partial | ✅ |
| **this** | ✅ (I/O) | ✅ | ✅ | ✅ | ✅ |

## 8. Phased build plan

- **Phase 0 — Scaffold.** *(done)* `uv` project, MCP server skeleton, `config`,
  `models` (incl. `MemoryType`), `MemoryStore` interface, SQLite store + schema,
  smoke test.
- **Phase 1 — MVP fast path.** *(done)* `remember`/`recall` with episodic capture +
  full hybrid contextual retrieval (vector + BM25 + RRF + rerank) on SQLite;
  `link` + bitemporal edges; `timeline` point-in-time. Four types stored via `type`.
- **Phase 2 — Graph + bitemporal depth.** Neighbors-as-context wired into the
  contextual blurb; `annotate`; `get_entity`/`search_entities`; richer
  point-in-time/history queries.
- **Phase 3 — Dreaming (internal).** Nightly job: LLM extraction →
  episodic→semantic/procedural consolidation → contradiction detection +
  bitemporal invalidation → self-schema update → contextual-blurb + index rebuild →
  lint (contradictions / stale / orphans). Scheduler via APScheduler/cron;
  `dream_now()` / `dream_status()`.
- **Phase 4 — Postgres graduation.** Implement `postgres_store` behind the same
  interface (pgvector + FTS/ParadeDB + edge tables or Apache AGE); run the same
  conformance suite; enable a concurrent dreaming worker.
- **Phase 5 (out of current scope) — External ingestion.** Nightly crawl/fetch/
  extract of external sites & sources, linked into the graph.
